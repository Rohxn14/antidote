# Design decisions

One entry per decision: what we chose, what we rejected, and why. Newest at the bottom.

| # | Decision | Rejected | Why |
|---|---|---|---|
| D1 | The demo opens with a malicious injection; an honest mistake (outdated page) is the optional second act | Opening with the honest mistake | Poisoning is the sharper, more recognisable threat (OWASP agentic Top 10); the same machinery handles both |
| D2 | Reasons are `Justification` nodes with `PREMISE` and `SUPPORTS` edges: AND inside, OR across | Plain `DERIVED_FROM` edges between beliefs | Plain edges cannot record which premises belong *together*. "A and B together imply C" and "A alone or B alone implies C" look identical with plain edges |
| D3 | Source `trust` (trusted, unverified, quarantined) is stored; support (`valid`) is computed. Sources carry an `origin` for lineage | Numeric trust scores | Two clear rules beat a threshold nobody can explain. `origin` stops two copies of one claim counting as independent |
| D4 | Stakes policy: automatic only if reversible, under $5,000 and surviving the loss of any single trusted origin. Configurable demo values | Hard-coded "safety rules" | The numbers are policy, not truth; `app/config.py` says so |
| D5 | Domain: procurement | Healthcare, finance | Easy to follow, money makes the stakes obvious, all data can be synthetic |
| D6 | Detection is rule-based or a user report; a human confirms the quarantine | An LLM detector | Detection is not the product: repair and the gate are. An LLM detector is itself injectable |
| D7 | Preview on a graph copy before repair, with a revision check. Repair approval is separate from purchase approval | Applying quarantines directly | Humans see the blast radius before committing; approving a memory fix must never approve spending |
| D8 | Permissions as a second root: cut | | Scope; two days |
| D9 | All writes go through `app/memory.py`; full least-fixed-point recompute after every write, in Cypher inside FalkorDB; computed fields are a cache; status can move both ways | Incremental updates; computing support in Python | Full recompute is obviously correct on a small graph. Running it in FalkorDB is what makes the graph do the real work |
| D10 | Action gate with order states, checked against the *current* graph at authorize and execute time | Trusting the state when the order was drafted | Memory can change between drafting and executing; that gap is exactly where poisoned decisions slip through |
| D11 | Benchmark against delete-source-only and full rollback, with four metrics | Claims without numbers | Measured comparison against the two obvious alternatives |
| D12 | Pitch: "graph-native recovery layer"; the honest limitation is stated in the README | Claiming guaranteed decontamination | We can only be as complete as the dependencies the agents recorded |
| D13 | Justifications are append-only: reusing an ID is rejected; to revise a reason, add a new justification | Editable justifications (MERGE + SET) | A justification is a historical record of why something was believed. Append-only also makes "exactly one SUPPORTS per justification" easy to guarantee |
| D14 | One Cypher query per logical write. It starts with `MATCH (m:Meta)` and bumps `m.revision` in the same query | Separate write and revision-bump queries | Atomic: the write and its revision bump happen together or not at all. A graph without the Meta node rejects writes instead of half-writing |
| D15 | A justification is rejected unless *every* cited premise exists (the query compares found vs cited counts) | Silently skipping unknown premise IDs | Skipping a premise makes a justification *easier* to satisfy: a typo would fail open. We fail closed |
| D16 | "All premises valid" is computed by counting (premises vs valid premises) | `all()` over a pattern comprehension | FalkorDB does not allow pattern comprehensions inside `WHERE` (found by probing v4.22) |
| D17 | Computed flags are read with `= true`, so a missing flag means "not valid" | Treating missing as valid | Fail closed: a node the engine has not processed yet is never trusted |
| D18 | The engine is checked against an independent reference (Dowling–Gallier linear-time Horn algorithm) on 25 random cyclic graphs, after random trust changes | Only hand-written cases | Valid beliefs are the least model of a Horn program; a second, unrelated algorithm agreeing on 125 graph states is strong evidence the Cypher is right. The reference lives in `tests/` only |
| D19 | Beliefs and decisions are create-once: re-adding the same ID with different content is rejected inside the query, before any edge is touched | Overwriting on MERGE | Silent overwrites would change what old justifications were about |
| D20 | "2 independent trusted roots" = on a throwaway copy, the order is valid when only trusted sources count, and stays valid after removing any single trusted origin. All trusted origins are tested | Counting distinct origins behind the decision; walking the graph to find "origins behind" | Counting is fooled by a justification that needs A *and* B. Walking back means alternating edge directions (`<-SUPPORTS-` then `-PREMISE->`), which a variable-length pattern can't express. Testing an origin that isn't behind the order simply changes nothing, so testing all is correct and simple |
| D21 | A human purchase approval can accept the stakes policy but never override missing support; approving a repair approves no purchase | "Approve" as an override | The climax of the demo: the manager clicks approve on the poisoned order and the gate still blocks it |
| D22 | A repair changes memory only; it does not touch order states. The gate blocks invalid orders when someone tries to act | Repair proactively cancelling orders | Keeps one place (the gate) responsible for actions, and it is checked at the last possible moment |
| D23 | Execute re-checks everything: an auto-authorized order that lost robustness goes back to `pending_approval`; one that lost support is `blocked` | Trusting the authorization | Same reason as D10: the graph can change between authorize and execute |
| D24 | The preview diff is Cypher on the copy: before quarantining, the copy stores `was_valid` / `was_holding`; afterwards one query lists what flipped | Diffing two downloaded snapshots in Python | Keeps the reasoning in FalkorDB; the scratch properties only ever exist on the copy |
| D25 | Orders already executed that lose support are listed separately as "needs a human" | Pretending repair can undo them | Memory can be repaired; real-world actions cannot. Honest about the limit |
| D26 | Stale preview: rejected and its copy deleted; the UI regenerates | Applying anyway | The preview a human approved must be the change that happens |
| D27 | A justification stores `premise_count` when created and holds only if that many premises are valid | Comparing against the PREMISE edges present now | Deleting a source (instead of quarantining it) removes edges, which would silently turn "S AND R" into "R alone". With the stored count, deletion fails closed. Found while designing the delete-source baseline |
| D28 | Agent output goes through `record_*` functions that check it: quotes must appear verbatim in the source; Buyer premises must be currently valid beliefs; the order amount is computed in code | Trusting structured output | The LLM proposes, the code checks. Structured output guarantees shape, not truth |
| D29 | The Researcher reads the raw page, HTML comments included, and is told to record claims without judging truth | Pre-cleaning pages; asking the LLM to spot lies | Realistic scraping agent; detection and repair are Antidote's job, not the extractor's |
| D30 | Tests and the default demo replay hand-authored fixtures in the exact LLM output format; real runs are recorded to `data/fixtures/live/` and labelled with the model | Calling the LLM during the demo | Deterministic demo and tests, no rate limits; honest labelling of which outputs came from a model |
| D31 | Benchmark ground truth comes from the independent reference (Horn least model) over the graph's structure; delete-only = DETACH DELETE with no propagation; rollback = restore the snapshot taken just before the poisoned ingestion; Antidote's repair time covers apply only (quarantine, recompute, verify, audit), since the preview happens before the human confirms | Grading Antidote with its own engine | An oracle that shares no code with the engine makes "0 residual, 0 collateral" a real measurement, not a tautology |
| D32 | Tracks: 01 (Agents That Act on Connected Data) + 02 (Agent Memory and Coordination). For 01, agents get Antidote's graph operations as MCP tools | 02 + 03 (Claude's suggestion: 03 fits with no extra work) | Rohan's call: the action gate is "acting on connected data"; MCP tools make the graph the agents' toolset |
| D33 | LLM provider: Groq through the OpenAI-compatible endpoint; JSON-schema mode with a JSON-mode fallback | Gemini | Rohan's choice; free tier, fast. The fallback covers models without strict schema support |
| D34 | Agents use the graph through MCP tools (`app/mcp_server.py`); the tool list deliberately has no approve-repair or approve-purchase tool, and read-only tools carry `readOnlyHint` | Letting agents call Python functions directly; an "approve" tool guarded by a prompt | The safety property ("agents propose, humans approve") is enforced by what the agent can call, not by instructions it might ignore. MCP also lets any host (Claude Desktop, Inspector) use Antidote's memory |
| D35 | Tool rejections come back as readable results (e.g. "not valid beliefs [...]"), not exceptions | Raising errors | MCP hides unexpected exceptions behind a generic message; a readable refusal lets the agent correct itself |
| D36 | The tool-using Buyer connects in-process (`mcp.Client(MCPServer)`) and the LLM picks tools in a loop; recorded transcript replayed in the UI | A fixed pipeline of calls | Track 01 asks for graph queries as agent tools and tool selection through MCP |
| D37 | One atomic query for the reset and ONE query per round (steps a and b together), 5 queries per recompute instead of 11 | Two queries per round (slightly easier to read) | Round trips dominate against FalkorDB Cloud: recompute 374 -> 114 ms, preview 1155 -> 502 ms. Correct even if (b) didn't see (a)'s writes in the same query (it would catch up next round; we stop only when both report zero). Measured: FalkorDB does make them visible, so the round count is unchanged |
| D38 | The quote check normalises BOTH the page and the quote the same way (tags and comment markers removed, typographic dashes/quotes unified, whitespace collapsed) | Normalising only the page | Found in the first live run: the model quoted registry table rows with their HTML tags; the text was on the page, the comparison was unfair. Still verbatim: the quote's text must appear on the page |
| D39 | Reusing an existing belief id (corroboration) is refused if the two claims' numbers conflict (neither set of numbers contains the other) | Trusting the agent's id reuse; requiring identical claim text | Found live: gpt-oss-120b filed the registry's "Vantor: ISO 9001" and the page's "Vantor: ISO 13485" under ONE id. Merged, the registry would have kept the page's lie alive after quarantine, and the $48,000 order would have survived. Identical-text matching would block legitimate paraphrased corroboration |
| D40 | Prompts show vendors as ids plus a vendor list; every schema field has a description; exact vendor names resolve to ids; bad agent output becomes a rejection, never an exception | Hoping the model guesses the format | Found live: names in id fields, `belief`/`claim` swapped, and one unknown vendor crashed `record_plan` |
| D41 | The default demo and the tests replay hand-authored fixtures; a real run (openai/gpt-oss-120b on Groq) is recorded in `data/fixtures/live/` and replays the same story with `DEMO_FIXTURES=live`; the live MCP agent transcript is shown in the UI | Making the live run the default | The scripted run shows the "survives via the registry" beat explicitly and keeps tests deterministic; the live run proves the agents really work |
| D42 | Numbers must come from the evidence: a claim may not state numbers its quote doesn't; a conclusion may not state numbers its premises don't; an order's quantity and unit price must appear in the beliefs it cites. Numbers are compared as runs of digits | Trusting a real quote to imply a faithful claim | Closes "laundering through a trusted source": e.g. "ISO 13485" claimed from a registry row that says ISO 9001. Checked on 62 real claims (22 scripted, 40 from gpt-oss-120b): zero false alarms. Digit runs also fixed a false conflict between "ISO 13485" and "ISO 13485:2016" in the D39 guard |
| D43 | Quarantining a source also quarantines every other source with the same origin (copies, mirrors), listed explicitly in the preview; it can be switched off | Per-source quarantine only | `origin` means "the same original claim"; a mirror of a poisoned page carries the same lie. Listing them in the preview lets a human catch a wrongly labelled origin before approving |
| D44 | Evidence strength for every belief and decision: unsupported / unverified only / single trusted origin / robust, computed on one throwaway GRAPH.COPY with the gate's what-if queries | Confidence scores | Antidote can't know what is true, but it can show how much each conclusion rests on sources you don't trust. Same machinery as the gate, so "robust" means exactly what the gate demands of automatic actions |
| D45 | A Playground: worlds are JSON (`sources`, `beliefs`, `decisions`, with `"because": [[...AND...], [...]]` for OR), loaded through memory.py into a private graph; quoted claims from sources that carry text go through the Researcher's checks | A free-form graph editor | Lets anyone design a world and attack it by hand with the real engine, gate and checks; validated before anything is written; five example worlds, each teaching one idea |
| D46 | Every GRAPH.COPY goes through `db.copy_graph`: serialized within a process and retried with backoff on "could not fork" | Calling `graph.copy()` directly | FalkorDB implements GRAPH.COPY by forking the server, and only one fork runs at a time. Investigating two intermittent test failures, a 4-thread stress test showed 49 of 100 concurrent copies failing; with the helper, 200 of 200 succeeded across two processes. The deployed demo (many visitors, previews, what-ifs, evidence) would have hit this |
| D47 | The poisoned page uses AgentDojo's published "important_instructions" (HTML comment) and "injecagent" (hidden element) templates with a fictional goal; the detector has named rule families mapped to AgentDojo's attacks; its "direct" template ("TODO: {goal}") is deliberately left uncovered and documented | Inventing our own injection; tuning rules to the exact templates | A published benchmark makes the attack credible (MIT licence, cited). Generic families rather than exact strings avoid teaching to the test; the README states the detector only catches known patterns |
| D48 | The numbers-from-evidence check stays strict (numbers must be in the quote itself, not elsewhere on the page); the Researcher's prompt says so | Accepting numbers that appear anywhere in the source | Found live: the model added product model numbers ("VM-40") from a heading. Page-wide matching would re-open the laundering hole (a registry page listing ISO 13485 for another supplier would vouch for anyone). Fail closed; 2 of 32 live claims refused, no decision affected |
| D49 | An external test set from RippleEdits (TACL 2024, MIT): the structure of 15 cases, entities anonymised, loaded as a trusted knowledge base, one unverified source per edit and justified dependent facts; each edit retracted in turn; ground truth = what loses all support per the reference solver | Loading the dataset as-is; using its labels as ground truth | Its facts concern real people with deliberately false edits (personal data, possible defamation), so only structure is kept. Its labels describe inserting an edit, not retracting one: 32 of 394 "should change" facts are also stated by its own knowledge base and must survive a retraction. The dependency edges are our encoding of its categories; the README says so |
| D50 | The app (Render, Virginia) and FalkorDB Cloud (AWS us-east-1) should run in the same area (prepared on the `region-virginia` branch; applied when the Cloud console allows a new instance) | Render Singapore with FalkorDB Cloud in Mumbai, the closest pair to India (first deploy); Render Frankfurt with FalkorDB Cloud eu-west-1 (Ireland), closer to India but in different countries; FalkorDB inside the app's container | Measured on the first live deploy: every statement cost ~62 ms (fastest 61.2 ms), the Singapore–Mumbai round trip, against ~1 ms locally. A full-speed replay took 27 s (1–2 s locally), a state refresh 2.7 s, and the capability walkthrough would have shown network time as Cypher time. FalkorDB Cloud's free tier offers ap-south-1, eu-west-1, us-east-1, us-east-2 and us-west-2; Render offers Oregon, Ohio, Virginia, Frankfurt and Singapore, and cannot move an existing service. Only the US pairs share an area. A distant visitor pays the distance once per request, not once per statement. An in-container database is wiped on every restart and drops the managed service |
| D51 | Every state between two queries leans towards "not supported"; recorded with the two steps that span several queries | Folding "approve" and "stop trusting" into single queries during the UI rebuild (an engine change) | A fact and its reason are two writes: in between, the fact has no reason and counts as unsupported. A reason is written with all its premise links in one query, refused if any is missing, and holds only if `premise_count` premises are valid (D27): a reason missing a premise would be easier to satisfy. Recompute starts from nothing holding, so a half-finished one under-reports support. Known gaps, both failing safe: "approve" checks support, then records "authorized" in a second query, but "execute" re-checks (D10); "stop trusting" distrusts, recomputes, then writes the audit record, so a crash before the record leaves the source distrusted but without the record of who approved it. Batching writes across queries to save round trips is ruled out for the same reasons; D50 removes the round-trip cost instead |
| D52 | An order resting on a document the security scan flagged is held: approval and execution wait until a person deals with the alert (by distrusting the document) | Letting a person approve anyway; a warning in the UI only | Rohan's review: a $48,000 order built on a page with hidden instructions could be approved with one click. The gate enforces the hold at the endpoint (`under_review`), so no client can skip it, and the state lists the documents holding each open order. "Rests on" is walked in FalkorDB one level per query: a reason points at both its premises and its conclusion, so the way down alternates edge directions and one variable-length pattern cannot follow it |
| D53 | Stopping trust in a document blocks the open orders that lost their support at once, and a blocked order says why: each premise that no longer holds, with the distrusted documents beneath it | Waiting until someone tries to approve (the order sat "waiting for approval" with no support left); the generic "no justification holds" | The preview already promised "orders that would be blocked". The reasons are computed from the graph, so they name the real facts and documents in any world, not just the demo's |
| D54 | Memory guard for FalkorDB Cloud's 100 MB: at most 25 cases, least recently used idle case evicted above 70 MB; the capability walkthrough runs one at a time, 10 s apart, and deletes leftover scratch graphs before it starts | 40 cases and no memory check | About 2 MB per finished case, and a walkthrough seeds a whole demo graph. A new visitor is still never refused |
| D55 | The guide is a case bar: the case's title, status chips and one suggestion, all derived from the memory; any document can be previewed for distrust, not only the flagged one | A numbered six-step tutorial ("Approve anyway?" was a step) | Rohan's review: the tutorial made the product feel scripted. Suggestions computed from the state fit any path someone takes, and previewing a trusted document (e.g. the registry) shows the engine's own answer: there, nothing is lost, because the suppliers' pages repeat each claim |
| D56 | Visitors can build their own case: the delivery deadline and, per supplier, price, delivery time, a certificate claimed on its page, the registry confirming it, and hidden instructions on its page. The documents and the agents' answers are generated from the form and go through the same runner steps, checks, writes, gate and scan as the story; the screen says no AI runs in a built case | A free-form JSON editor (the Playground's format); turning on live AI for everyone | Rohan's review: one story can look fabricated. A form people can change in seconds shows the engine reacting to their choices, including cases where the injection steers the Buyer to the priciest supplier. The agents follow two stated rules (record what each document says, hidden text included; order the cheapest qualifying supplier unless a page says another is the only certified one), so nothing pretends to be AI |
| D57 | Verification hold: an order at or above $5,000 waits while any conclusion it rests on (a fact an agent concluded from other facts, such as "Vantor meets the ISO 13485 requirement") holds only because unverified documents say so. Tested on a throwaway GRAPH.COPY where only trusted documents count | Approving with a warning ("nothing trusted confirms it") and leaving it to the person; requiring trusted support for every premise | The "plain lie" case: no hidden text, so no alert, and a $48,000 order resting on the supplier's own word could be approved. Prices come only from the supplier's page, so demanding trusted support for every premise would hold every order; the conclusions are what must be confirmed |
| D58 | Every judgement the product makes is a Cypher query in FalkorDB, including the ones that were finished in Python over downloaded flags: which cited facts the Buyer may rely on, which conclusions fall in the trusted-only world, which documents among an order's foundations are distrusted or under review, and each node's evidence level (each what-if world's answer is written onto the copy, and one query combines them). Python keeps the loops (rounds, levels, worlds), the stakes policy, the order's state transitions, the agents, the hidden-text scanner and the wording | Leaving the Python filters (they gave the same answers) | The hackathon's rule: "core logic must run as Cypher inside FalkorDB, not as Python over downloaded data". An audit found Python reading every node's flag and filtering it (`support.status()` in the Buyer and the case builder; filters and set differences in the gate and the evidence levels). Same results, same tests. `support.status()` remains only where a repair's preview is compared with its real result: that spans two graphs, so it cannot be one query |
| D59 | The security scan and a new conflict check run right after the Researcher reads, before any agent concludes or decides. A flagged document goes under review (`Source.review`): the support engine counts it for nothing, and the suppliers its facts are about are suspended (`Vendor.status`), which the gate enforces. A person then blacklists the supplier (distrusting the page, previewed as what rests only on it) or clears a false alarm | Scanning after the Buyer planned and holding the order (D52); blacklisting automatically | Rohan's review: an order was drafted for the supplier that hid instructions, and only then held. Checking first means no agent and no order ever rests on a flagged page, and one rule (an invalid source) covers the Buyer, the gate, the live LLM's prompt and the MCP tools. Blacklisting stays a person's call: the scan matches patterns and can be wrong, and anyone able to plant hidden text on a page about a supplier could otherwise get a competitor blacklisted |
| D60 | Conflict check in Cypher: an exclusive claim ("the only ISO 13485-certified supplier") read in a document we do not trust, against certification claims for other suppliers read in trusted documents. Claims carry `standard` and `exclusive`, recorded by the Researcher (and asked of the live LLM) | Comparing claim texts; an LLM judge | Rohan's review: "the agent believes Vantor is the only certified supplier while the registry says otherwise". Structured tags make the contradiction a graph pattern, so it works in any case built, with or without hidden text. Its limit is stated: a claim nothing trusted contradicts still steers the Buyer, and only the verification hold stops that order |
| D61 | The story's recorded Buyer is the case builder's planner (cheapest qualifying supplier on supported facts, unless a supported fact says one is the only certified one); the Researcher's answers stay recorded. The builder takes 3 to 6 suppliers and seven presets | One fixed recorded Buyer answer per scenario | With documents checked first, the Buyer's answer depends on what memory supports at that moment (under review, cleared, distrusted); a fixed recording could not follow a person's choices. With `DEMO_FIXTURES=live` the Researcher's answers still come from the recorded gpt-oss-120b run (whose claims carry no `standard` tags, so only the scan flags the page there); the recorded Buyer answers are no longer replayed |
